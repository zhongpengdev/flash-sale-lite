# Flash Sale Lite (轻量级高并发秒杀与订单履约系统)

> **面向目标**：针对计算机专业应聘「Python 后端开发实习生」的工程级标准项目。结构清晰、工程规范、开箱即用，核心围绕**高并发防超卖 (Redis+Lua)**、**异步削峰 (Celery)**、**接口滑动窗口限流**与**超时未支付延时回滚**四大经典后端场景设计。

## 1. 架构设计与技术栈 (Architecture & Tech Stack)

### 技术栈选型
- **Web 框架**：FastAPI (Python 3.11+, 纯异步 `async/await` 响应式 API)
- **数据库**：PostgreSQL 15+
- **ORM 与会话**：SQLAlchemy 2.0 (FastAPI 走 `asyncpg` 异步会话，Celery 走 `psycopg2` 同步会话)
- **缓存与原子操作**：Redis 7+ (基于 `redis.asyncio` 异步驱动与连接池)
- **异步任务队列**：Celery (Redis 隔离 DB 作为 Broker 与 Result Backend)
- **数据迁移**：Alembic
- **容器编排**：Docker Compose

## 3. 极简一键运行指南 (Quick Start)

### 步骤 1：启动基础服务 (PostgreSQL & Redis)

若使用 Docker：
```bash
docker compose up -d
```
> 注：若本机已安装并运行 PostgreSQL (端口 5432) 和 Redis (端口 6379)，可直接跳过 Docker 步骤，确保 `.env` 中的账密对应即可。

### 步骤 2：安装 Python 依赖

```bash
# 建议创建独立虚拟环境
python3 -m venv .venv
source .venv/bin/activate

# 安装项目依赖
pip install -r requirements.txt
```

### 步骤 3：数据初始化与缓存预热

运行初始化脚本：创建商品表、100 位测试用户，以及初始物理库存为 10 的秒杀测试商品，并将库存预热至 Redis：
```bash
python scripts/init_data.py
```

### 步骤 4：启动主服务与异步 Worker

**窗口 1：启动 FastAPI Web 服务**
```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```
服务启动后访问交互式接口文档：[http://localhost:8000/docs](http://localhost:8000/docs)

**窗口 2：启动 Celery 异步落库 Worker**
```bash
celery -A app.worker.celery_app worker --loglevel=info --concurrency=4
```

## 5. 面试核心高频考点与答题口述指南 (Interview Q&A)

针对 Python 后端面试中高频出现的秒杀系统设计问题，整理了标准解答口径：

### Q1：为什么不能直接用 MySQL 的 `SELECT ... FOR UPDATE` 或乐观锁防超卖？
- **口述回答**：
  > “直接在 MySQL 里加锁（悲观锁行锁或乐观锁 CAS 版本号）在低并发下可行，但在秒杀瞬间有数万甚至数十万请求涌入。
  > 如果所有请求都打到 MySQL，会导致所有事务排队争抢同一行记录的互斥锁（X 锁），引起大量事务等待与超时，数据库连接池瞬间被打满，CPU 飙升到 100%，从而造成整个数据库服务雪崩。
  > 我们的方案是将扣库存动作前置到 Redis 内存中（微秒级响应），MySQL 不直接承受秒杀峰值流量，而是由 Celery Worker 异步匀速削峰落库。”

### Q2：为什么 Redis 扣减库存必须使用 Lua 脚本？单纯使用 `DECR` 行不行？
- **口述回答**：
  > “单纯使用 `DECR` 是不够的。因为秒杀业务不仅要扣库存，还要做**单人限购校验**（防止同一个刷子买多件）以及**库存是否大于零的判断**。
  > 如果在 Python 代码里分步调用 `SISMEMBER`、`GET`、`DECR` 和 `SADD`，由于网络 I/O 穿插和并发执行，在判断库存大于 0 到执行 DECR 之间存在竞态条件（Race Condition），必然导致超卖。
  > Redis 内部是单线程执行命令的。Lua 脚本在 Redis 中执行时被作为一个原子操作（Atomic Unit），期间不会穿插任何其他命令。我们在一个 Lua 脚本内同时完成‘查重 -> 查库存 -> DECR 扣减 -> SADD 记录用户’，从而在内存级百分百杜绝超卖。”

### Q3：为什么 FastAPI 使用异步 `asyncpg`，而 Celery Worker 任务使用同步 `psycopg2`？
- **口述回答**：
  > “FastAPI 是基于 ASGI 的异步事件循环模型，使用异步驱动 `asyncpg` 能够在等待网络 I/O 时让出执行权，大幅提升单机接口的并发吞吐能力。
  > 但 Celery 默认是 prefork 多进程模型。如果在主进程中创建了 asyncio 事件循环和异步连接池，fork 出的子进程会继承父进程的套接字和状态，在子进程中调用 `asyncio.run()` 会引发著名的跨进程事件循环冲突 `RuntimeError: Task got future attached to a different loop` 或连接池死锁。
  > 因此，Worker 任务采用独立的同步连接池（`psycopg2` + 上下文管理器），不仅符合 Celery 标准范式，而且工程稳定性最高。”

### Q4：Redis 扣减成功但 Celery 任务消费失败怎么办？最终一致性如何保障？
- **口述回答**：
  > “这是典型的分布式最终一致性问题。我们采取了三层保障策略：
  > 1. **Celery 任务幂等性与重试**：落库任务以全局唯一 `order_id` 为幂等键，开启 `acks_late=True` 和 `max_retries=3`，在遇到瞬时网络抖动或数据库锁超时自动重试；
  > 2. **数据库级物理约束兜底**：商品表的 `stock` 字段添加了 `CHECK (stock >= 0)` 物理约束，落库 SQL 采用原子更新 `UPDATE products SET stock = stock - 1 WHERE id = :id AND stock > 0`；如果行数为 0 则触发事务回滚并反向回滚 Redis；
  > 3. **超时自动回滚补偿**：每个订单生成后会挂载一个 15 分钟后的延时任务 `cancel_unpaid_order_task`，若超时未支付，不仅将订单标记为已取消、恢复 DB 库存，还会调用 Redis `INCR` 和 `SREM` 恢复缓存库存，实现最终闭环。”

### Q5：限流中间件采用滑动窗口（Sliding Window）相比固定窗口好在哪里？
- **口述回答**：
  > “固定窗口计数器（Fixed Window）存在‘临界突发缺陷’。例如限制 1 秒最多 5 次请求，若攻击者在 0.99 秒打入 5 次，在 1.01 秒又打入 5 次，虽然两个独立自然秒内都没有超过 5 次，但在 0.02 秒的临界区间内瞬间涌入了 10 次请求，失去限流意义。
  > 我们基于 Redis 的 ZSET 实现了滑动窗口日志（Sliding Window Log）：以毫秒时间戳为 Score 和 Member。每次请求来时，先通过 `ZREMRANGEBYSCORE` 剔除 1 秒以前的旧记录，再通过 `ZCARD` 统计当前滑动窗口内的实际请求数，精准保证任意连续 1 秒内请求次数绝不超过阈值，拦截效果更平滑可靠。”
